# Feature-per-File（F2F）· 以功能为文件

> **Feature-per-File: Refactoring Code Organization for AI Programming — A Data-Engineering Perspective**
> 面向 AI 编程的代码组织重构 —— 一个数据工程视角

📄 成品：[以功能为文件-AI编程重构论文.pdf](以功能为文件-AI编程重构论文.pdf)

---

## 问题

AI 编程（大模型生成与修改代码）正在成为主流生产方式，但其失控症状日益显现：

- 模型倾向于**只增不删**的增量式修改，代码熵持续累积；
- 跨文件、跨层次的改动**难以审阅**；
- 故障发生时**问题定位模糊**；
- **迭代半径不可预估**。

## 方案

**以功能为文件（F2F）**：放弃按技术职责横向分层（Controller → Service → Mapper）的组织方式，

- 以**功能**为最小自治单元，一个文件贯通从**入口 → 业务处理 → 数据访问**的完整链路；
- 文件之间**零耦合**，只能通过数据（表、缓存、消息、文件）衔接；
- 维护采用**替换式**——为功能重新生成一份完整文件做整体替换，并辅以**历史版 / 运行版 / 开发版**三版本并存模型。

## 三重根源论证

| 根源 | 要点 |
|---|---|
| 训练数据污染与分布继承 | AI 从人类代码中习得的分层与复用习惯，是人类时代的效率产物，而非 AI 时代的最优解 |
| 复用经济学的反转 | 当代码生成成本趋近于零，复用的收益消失而耦合的成本凸显——**冗余取代复用成为效率来源** |
| 修改半径的结构性放大 | 功能逻辑被横向打散到多个文件，迫使 AI 的每次修改都成为跨文件的一致性维护作业 |

## 理论性质

- **影响有界性** —— 一次修改的影响范围可被文件边界界定；
- **替换友好性** —— 重写优于修补；
- **审阅与定位友好性** —— 一个文件即一条完整数据流，可一路读到底。

论文另以 **Java MVC 三层**为靶例、**Django MTV** 等其他横向切分范式为佐证，说明问题的普适性，并讨论了冗余的正当性与方案的适用边界。
